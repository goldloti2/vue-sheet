# 設計取捨

各份文件只寫已經定好的規則；為什麼這樣做、為什麼不那樣做，集中記錄於此，供維護框架時參考。依主題分節，各節的條目大致依對應文件的順序排列；最後兩節為評估後決定不做的項目，以及已知的權宜作法。

---

## 架構與頁面

**為什麼頁面仍然手寫**
每張表的顯示方式差異大，還有跨表組合的頁面，無法由 schema 產生；重複的部分以元件庫、composables 與頁面範本壓低。

**為什麼 KeepAlive 的 key 帶完整網址**
不帶的話，同一個路由換 id（`/表名/A` → `/表名/B`）對 Vue 而言是同一個元件、同一個 vnode，會就地更新：頁面須自行跟著 id 重新載入，各筆的元件狀態也無法分開保留。帶完整網址後，一個實例只對應一個網址，路由參數對它而言是常數。代價是 KeepAlive 從「每個元件一份」變為「每個網址一份」，因此須以 `max` 收斂；連續切換超過 50 筆而不回到列表時，列表頁會被擠出快取，展開狀態隨之消失。

**為什麼被快取的頁面仍在運轉，以及 KeepAlive 的規則由此而來**
KeepAlive 的 `deactivate` 只搬移 DOM，不會暫停元件的 effect；而 `onDeactivated` 於渲染之後才執行，比 pre-flush 的 `watch` 還晚。因此被快取的頁面仍會對外部變化重新計算、重新渲染，而外面已經換頁了。舊的換頁動畫中，離場的頁面是活的 DOM，直接造成「閃一下錯誤內容」；改用 View Transitions 後離場的一側為截圖，不再看得到，但頁面回到畫面時仍帶著背景期間算出的狀態。流進被快取頁面的東西只有兩種：路由參數（讀一次即固定）與共用快取（任其改變）。各條規則的理由：

- `[id]` 頁面不跟著路由變化：離開中的頁面會讀到目的地的 id
- 快取改變時任其改變：資料確實被刪除時，顯示「找不到這筆資料」即為正確的結果
- 新增頁於 `onActivated` 重建表單：網址固定，不重建會停留在上次的內容，也讀不到新的預設值；編輯頁「離開後再回到同一筆」亦為同一份實例，不重置的話上次未儲存的輸入會留著，容易被誤存
- Teleport 出去的浮動元件自行處理進出場：否則離開的頁面會把按鈕留在畫面上
- 列表載入中不以 `v-if` 整個替換：同步鈕會重新抓取所有已載入的表，每次都會卸載重建，`GroupedList` 的展開狀態隨之消失
- 捲動位置另外記錄：KeepAlive 保留的是元件，視窗的捲動位於元件之外

**為什麼換頁動畫使用 View Transitions，而非 `<Transition>`**
`<Transition>` 須看到新舊兩個不同的元件才會播放。儀表板的展開與縮回網址不變，KeepAlive 的 key 相同，前後是同一個元件，`<Transition>` 無從觸發。View Transitions 由瀏覽器截下 DOM 更新前後的畫面再播放動畫，不論前後是否為同一個元件，因此換頁與展開共用同一套。

- **導覽失敗時略過動畫**：畫面沒變，滑動兩張相同的截圖沒有意義
- **滑動整個畫面（`root`）的截圖，而非替內容區命名**：`root` 的截圖即為當下看到的畫面，不受捲動位置影響；單獨命名內容區時，元素的位置會隨捲動改變，截圖於動畫中會上下跳動
- **舊做法的兩個限制**（`<Transition>` + `<KeepAlive>`，改用 View Transitions 後皆不復存在）：離場的一側套用的是該 vnode 上次啟用時的 transition hooks，方向須改以屬性選擇器讀取；頁面的 root 須為單一元素，因此三個版型都在外面包一層 `div`，目前仍保留

**為什麼 App Bar 的動作經由 provide/inject，FAB 與 `RecordNav` 經由 Teleport**
App Bar 屬於 `AppShell`，頁面只需將動作交給它，不需實際搬移 DOM；FAB 與 `RecordNav` 的箭頭為 `position: fixed`，放在頁面中時，帶有 `transform` 或 containment 的祖先（例如儀表板的面板）會成為它的定位基準，按鈕便不再貼著螢幕，因此送至 `body`。換頁動畫中三者皆另有 `view-transition-name`，不隨頁面滑動。

**為什麼三個登記處皆只採用一個頁面的內容**
App Bar 的動作、底部動作列與 FAB 皆經由同一個 `registerActions`（`useActionSlot.ts`），同一時間只採用一個頁面的動作。因此必須以 `isActive` 擋下被 KeepAlive 快取的頁面：這些頁面仍在全速運轉，其動作一旦改變，便會蓋掉目前頁面的動作。

**為什麼表單的按鈕在螢幕最底端**
「取消」與「送出」始終位於拇指可及之處，不必將長表單捲到最後才能按到。表單本來就是「按下才算完成」的頁面，此時不應讓使用者分心切換頁面，因此直接取代底部導覽列。

**為什麼完成動作後以 `leaveAfterAction` 離開，而非 `router.push`**
使用 `push` 會將已完成任務的表單頁留在歷史中，按上一頁又回到它：編輯頁會是舊的表單，刪除後的詳細頁更是已不存在的資料。

**為什麼取消鈕本身不詢問是否離開**
取消鈕觸發的導覽會經過 `useLeaveGuard`，取消鈕若自己再問一次，使用者會被問兩次。

**為什麼連續動作的第二步起一律詢問**
這張表單可能尚未填寫任何內容，但前面的步驟已寫入資料，離開即等於整條流程收回。

**為什麼 `detailOrder` 與 `formOrder` 分開**
詳細頁與表單頁的需求不一定相同。

## 資料表與 schema

**為什麼以 `TableSchema<Row>` 宣告**
讓 TS 檢查 schema：`key`、`labelColumn`、`searchable`、`sortable`、`detailOrder`、`defaultSort` 只能填 Row 有的欄位名，`type` 須與該欄位的值型別相符，虛擬欄位 `value` 的參數亦直接為該表的 Row。

**為什麼不以 row number 作為主鍵**
排序、刪除、插入都會讓 row index 位移。

**為什麼主鍵是一般欄位上的標記，而非獨立的系統欄位**
與父表共用 id 的一對一延伸表需要主鍵本身是 `ref`，商品編號這類自然鍵需要由使用者輸入；兩者都要求主鍵能像一般欄位一樣出現在表單、詳細頁與搜尋中。標記的形式與 `labelColumn` 相同，`row.id` 與該欄恆等：store、路由與關聯照舊只讀 `row.id`，主鍵建立後不能修改，因此兩者不會不同步。

**為什麼主鍵建立後不能修改**
主鍵一改，子列的 ref、待推送佇列（後端在推送前仍是舊 id）、詳細頁的網址、KeepAlive 的快取、列表順序與選取都記著舊 id，須全部連帶更新。可修改的 id 留待確實需要時再做，見 ROADMAP 的「未完成」。

**為什麼主鍵的唯讀由呼叫端判斷，store 另外再擋**
新增與編輯共用同一份 `formOrder`，新增時要填的主鍵在編輯表單中必然出現，設計者無法只從編輯表單拿掉，因此由表單依「是否修改既有的列」自動設為唯讀：`FormPage` 看 row 是否已有 `id`，`askFields` 看是否給了 `rows`。`setFieldAction` 這類不經過表單的寫入，由 store 的 `update` 作為最後一道防線。

**為什麼 `create` 擋下重複的 id 與剛被刪除的 id**
後端把已存在的 id 當成重送，直接略過；使用者輸入重複的編號時，那一筆會被無聲吃掉，因此須在前端寫入前擋下。剛被刪除、尚未推送的 id 若再新增，佇列會把刪除與新增合併為一筆新增，而 Sheet 上的舊列仍在，新增同樣會被略過，因此推送之後才能再使用。

**為什麼主鍵不以 `'` 開頭**
`'` 是 Sheet 的純文字前綴，存進去後不算內容，`'A1` 讀回來即為 `A1`，與前端記的 id 不同而找不到列。

**為什麼主鍵只能使用 `encodeURIComponent` 不會改變的字元**
主鍵會直接接進網址（`/表/id`），沒有編碼：`/` 與 `\` 會被當成路徑分隔，`?` 與 `#` 之後變成查詢字串或錨點，`%xx` 會被 vue-router 解碼成別的字。改為組網址時編碼雖可容許任何字元，但框架、範本與各頁面約二十處組網址的地方都須改用同一個函式，日後新寫的頁面也容易漏掉；主鍵多為英數編號，因此選擇限制字元，代價是主鍵不能有中文與空白。`.` 與 `..` 能通過這項檢查，但即使編碼成 `%2E`，瀏覽器依網址規範仍視為「目前這層」與「上一層」，只能擋下。

**為什麼 `update` 不把主鍵寫回 Sheet**
值沒有變，寫回只是多一格無意義的寫入；後端也不必處理「更新主鍵那一格」的情況。

**為什麼表頭使用對外名稱**
方便直接開啟 Sheet 檢查或手動修改資料。程式中另用 `key`，英文、好輸入且不會改變。

**為什麼只有部分型別補上單引號**
- `number` 與 `date` 不補：它們本來就應讓 Sheet 存為數字與日期，表上的 `SUM` 與日期格式才能使用
- `duration` 不補：實測不會被 Sheet 改寫
- `ref` 不補：它的值是對方的 id，必須與主鍵一字不差；而主鍵本身不能補，後端須以 id 與 Sheet 上的顯示值比對才找得到那一列。兩邊規則一致才不會脫鉤，只有一邊補的話，`row.欄位 === 對方.id` 會對不上，關聯無聲斷掉
- 主鍵不以數字或 `=`、`+`、`-` 開頭，也不含 `/`：否則會被 Sheet 解析為數字、公式或日期而找不到列；這也使主鍵不會符合任何需要補單引號的形狀，`text` 型別的主鍵因此同樣不會被補
- 這件事只有前端做得到：後端只認得表頭，分不出「文字欄位中的 `0912`」與「數字欄位中的 `0.5`」

**為什麼 `date` 讀進來時歸零到午夜**
Sheet 上手動加了時間時，「看起來一樣的兩列」排序或篩選才不會不同。

**為什麼 `duration` 是「時:分:秒」的字串**
Sheet 上即為 `2:30:00`，開啟來看得懂。表單使用一般的文字框，是因為原生的 `type="time"` 容不下超過 24 小時的值；排序與篩選換算為秒，`9:30:00` 才不會排到 `10:00:00` 後面。`duration` 不兼作時間點：它沒有上限，也沒有上午與下午的概念。

**為什麼 `boolean` 的空值維持空，而非當成否**
「還沒決定」與「否」是兩件事，空的當成否會把前者無聲地改成後者；空值也讓 `required` 仍有意義。

**為什麼 `boolean` 在 Sheet 上不用核取方塊，在表單中不用開關或勾選框**
核取方塊、開關與勾選框都只有兩種狀態，無法表示空；Sheet 上直接存 `TRUE`／`FALSE`／空白，表單則用兩顆互斥的按鈕，再按一次即回到空。

**為什麼 `formatColumnValue` 以參數區分顯示與寫回 Sheet**
兩者大多相同，只有 `boolean`（是／否 與 `TRUE`／`FALSE`）和 `ref`（對方的名稱與 id）不同，集中在同一個函式中分支，不必另外維護一份寫回用的格式化。`ref` 原本寫回 id 只是因為送進 `serializeRow` 的值沒有掛 getter、拿不到父列；明確指定寫回模式後，即使傳入掛了 getter 的列，也一律寫 id。

**為什麼 `boolean` 寫回 `TRUE`／`FALSE`，而非顯示的「是」「否」**
Sheet 會把 `TRUE`／`FALSE` 解析為布林值，讀回來的顯示值仍是 `TRUE`／`FALSE`；寫「是」「否」則只是文字，換了語言或格式就對不上。

**為什麼 Drive 的圖片使用縮圖網址**
沿用瀏覽器已登入的 Google 帳號，不需經過後端，也沒有 CORS 的問題。

**為什麼虛擬欄位與 `columns` 分開放**
`coerceRow`、`serializeRow` 與表單因此完全不需要知道虛擬欄位的存在。

**為什麼 row 上的 getter 不可列舉**
寫回後端時才不會誤送。

**為什麼跨表的值是 getter，而非在父表存一份**
雙向維護容易不一致（新增子列須記得更新父列），而且 Sheet 上會多出沒人維護的欄位。改為讀取時計算，真相永遠只有一份，新增或刪除子列也不需維護任何東西。代價是載入一張表時，須把它的父表與子表一起載入，row 上的 getter 才有東西可讀；以目前的規模並無影響，而要顯示關聯資料本來就得整張載入。

**為什麼子列建立索引**
`$子表_欄位key` 若每次讀取都重新掃描整張子表，一個列表頁每列讀好幾次就是 N×M 次比對。改為每條關聯一份「父 id → 子列」的索引（整張子表排序一次後分組），放在 `computed` 中，子表的陣列被替換時才重建，讀取只是查表；回傳的陣列身分也因此穩定。

**為什麼子列 getter 的名稱帶上欄位名**
不需任何設定，看 schema 即可推得名稱；同一張子表有兩個 ref 指向同一張父表時，兩條關聯各有各的名稱。

**為什麼合法性驗證只在前端**
Sheet 本來就能手動開啟來修改，後端檢查合法性也擋不完整，不如把責任明確劃給前端一份。後端只保留結構完整性：寫錯的欄位名會直接在 Sheet 上長出一欄新表頭或寫錯儲存格，這一項不能省略。新增表單的初始值同理，只存在於前端，後端不會替沒給的欄位填任何值。

**為什麼 store 的 `create`／`update` 再驗一次**
擋下繞過表單的程式錯誤。

**為什麼 `schema/` 根目錄只放純函數**
不碰 reactivity，store、元件與 composable 皆可直接呼叫；反應式的包裝另放於 `composables/data/`。

**為什麼 `allowCustom` 與 `suggestFromData` 是兩個開關**
「清單自己長」不一定是好事：輸入錯誤的值也會變成建議，而清單只會變長、不會收回。因此分開，由設計者自行決定。

**為什麼分組的 `sortKey` 與 `label` 分開**
依顯示字串排序會出錯，例如「10月」會排在「2月」前面。

**為什麼 `TableSchema<Row>` 只做單向檢查**
Row 介面仍須手寫（虛擬欄位的 `readonly xxx`、store 掛上的 `readonly $欄位key?`），泛型不會反過來從 schema 產生介面：那需要兩段式的 builder 加上跨表的延遲查表，schema 便不再是一眼可看完的物件字面值，不值得。框架端一律使用不帶參數的 `TableSchema`，其 Row 預設為 `any`；不使用 `object`，是因為 `keyof Row` 會讓 TS 把 Row 判為逆變，`TableSchema<XxxRow>` 將無法指派給 `TableSchema<object>`。

**為什麼預設值經由 `history.state`，而非 query param**
值不出現在網址上；比起全域變數，**值綁在那一筆歷史紀錄上**，不會殘留下來影響之後不相關的表單。

## 資料流與佇列

**為什麼沒有「只重抓一張表」的 API**
store 會自行補齊快取，頁面沒有需要自己補資料的時機。

**為什麼表單一律送整列**
payload 較大，但省去在表單中比對原始值的複雜度。

**為什麼新增的 id 由前端發**
重送因此變得安全：`create` 的語意為「id 不存在即建立、已存在即視為已完成」，整批重送不需記錄哪幾筆已成功。後端仍須阻擋重複的 id，因為 Sheet 可以手動開啟修改。

**為什麼推送不回傳資料列**
寫入的當下前端快取已改好，而推送成功後 `refresh()` 本來就會重新抓取。

**為什麼同步鈕在推送失敗時不重抓，且重抓的範圍包含載入失敗的表**
推送失敗後重抓，會無聲蓋掉未推送的變更。載入失敗的表不在快取中，不另外算進去的話，第一次就載入失敗的表按同步也不會再試。同步鈕同時也是重新整理，因此平常一律可按。

**為什麼表單開著時停用同步**
避免改到一半的內容被同步的結果蓋掉。

**為什麼同步鈕不經由 `useAppBarActions`**
那條管道是給頁面登記動作用的，混進去會把頁面的動作擠進 ⋮ 選單。

**為什麼快取不分「已送出」與「未送出」**
畫面不應關心一筆是否已送出，只需顯示使用者眼中的現況；需要分辨的是 `pending`，那是 `flush` 的事。跨表算出的值（例如父表顯示子表的加總）讀的是同一份共用資料，會自動跟著重算，不需任何跨表的失效機制。

**為什麼佇列存序列化後的字串，而非 `Partial<Row>`**
那本來就是要送給後端的形狀，`flush` 取得即可送出；而且其中沒有 `Date` 物件，日後要存入 `localStorage` 時 `JSON.stringify` 可直接使用，不必回頭修改資料結構。

**為什麼存檔點存整張表，而非逐筆**
流程進行中沒有其他寫入者：使用者正在填寫表單，而 `flush()` 於流程進行中會被擋下（否則按了同步就會把半成品推進 Sheet，之後想回滾也無法回滾，存檔點只能還原記憶體）。因此整張還原與逐筆還原等價，但簡單許多：`patch` 本來就是整個陣列替換，佇列的 `PendingOp` 也一律建立新物件、不就地修改，淺層複製即足夠。

**為什麼存檔點是隱式的（store 中的環境狀態）**
流程期間的寫入不是連接器做的，而是表單頁做的。`useCreateForm` 與連接器隔著一次導覽，是不同的元件，拿不到明確傳下去的交易物件（函式無法放進 `history.state`）。因此 `activeFlow` 放在 store 中，由 `store.create`／`update` 自行查看。

**為什麼假後端與真後端回傳相同的形狀**
上線時只需於 `.env` 填入一個網址，`appScript.ts` 以外的程式碼皆不必修改。為此假後端亦與真的 Sheet 一樣只存原始字串，型別轉換同樣交給呼叫端的 `coerceRow`。

## 動作

**為什麼所有動作使用同一種描述**
同一個動作可以直接搬到另一個位置，不需要修改。

**為什麼 `icon` 一律要給**
底部動作列雖然只顯示文字，但形狀統一，同一個動作搬到別的位置時不必補上任何東西。

**為什麼 `PageAction` 只有 `onClick`，沒有宣告式的 `to`**
求值時機：動作物件在頁面 setup 時即建立，寫進 `to` 的值那時就已定型，切換頁籤後再按新增會帶到舊的狀態。統一為一種也避免兩者都設定時變成「導覽並執行」兩件事一起發生。代價是動作渲染為 `<button>` 而非 `<a>`，失去中鍵開新分頁與連結的無障礙語意；本框架的動作大多位於 FAB 與 App Bar，影響不大。

**為什麼 ref 欄位的那一格是按鈕，而非連結**
從 `<RouterLink>` 改為 `<button>` 後，中鍵開新分頁的功能消失，與 `PageAction` 沒有 `to` 是同一個取捨。導覽使用 `push`，回來時詳細頁仍在。

**為什麼欄位動作不是內建的**
ref 的「前往對方」與開啟網址、改為今天一樣是 builder，需要就列入、不需要就不列，不設「空陣列代表內建」這種第三種狀態。

**為什麼 `confirm` 是宣告式，`askFields` 不是**
`confirm` 對每個動作都一樣，動作本體不需知道結果，因此做成語法糖。`askFields` 的結果是動作要拿去使用的，只能在 `onClick` 中自行 `await`。

**為什麼 builder 是一般函式，而非 composable**
同一個 builder 須用於詳細頁當前那一筆（會變動的 Ref）、欄位動作，以及列表的每一列（view 的 `actions`）。若 builder 本身為 composable（接收 Ref、回傳 computed），每一列每次求值都會建立一個 computed，也違反 composable 僅於 setup 中呼叫的慣例。改為一般函式後，每次呼叫只建立一個普通物件；只有交給 FAB 與 App Bar 的那一層需要隨資料更新，由 `useAction`／`useRowAction` 負責。

**為什麼以列為參數的動作由頁面綁定，而非 `use表名Actions`**
「綁定至當前那一列」只在詳細頁成立；列表的每一列則各自呼叫。若由 `use表名Actions` 負責綁定，它便須得知自己供哪一種頁面使用，列表也無法取得可逐列呼叫的版本，同一個動作勢必定義兩份。因此 `use表名Actions` 只負責定義，綁定交由需要的頁面（`useRowAction`）處理。

**為什麼刪除後自動離開**
「刪除目前所顯示的那一列後離開該頁」在任何頁面皆成立，不應要求每個詳細頁各自傳入 `leaveAfterAction`；若由頁面傳入，漏傳時仍可通過編譯，刪除後卻停留在「找不到這筆資料」的畫面。因此 `deleteAction` 於刪除後檢查目前的路由是否為該列的詳細頁，若是則自動離開；`onDone` 只用於其他額外的處理。

**為什麼 `use表名Actions` 的每一項是單一動作，而非陣列**
一個位置放哪幾個動作是頁面的決定，因此由頁面組成陣列（`[editAction.value, deleteAction.value]`）。不適用的動作以 `null` 表示，由接收的位置略過；`null` 的處理集中於框架的幾個位置元件中，頁面與 `use表名Actions` 都不需判斷。早期的 builder 一律回傳 `ComputedRef<PageAction[]>`，以空陣列表示不適用，但這讓單一動作也必須包成陣列，而且陣列的名稱與內容（只有一個動作）不一致。

**為什麼 `null` 由繪製按鈕的元件處理，而非中間層**
不同位置對 `null` 的解讀不同：FAB、App Bar、子表區塊、deck、profile 與 gallery 會略過它，card 與詳細頁的標頭則把它當成空格、保留位置。只有最後繪製按鈕的元件知道 `null` 在該處代表什麼，若於版面元件或登記機制等中間層統一過濾，空格的資訊便會遺失。

**為什麼流程的第一步 `push`，之後 `replace`**
`push` 是為了保留發起流程的那一頁，`replace` 則讓做完的表單不留在歷史中。結果是歷史始終只有「起點 → 目前這一步」兩筆：任何一步按返回或取消都回到起點，流程結束後也能從終點返回起點。全部使用 `replace` 的話，起點會被第一步取代，取消時便無處可去。

**為什麼流程是 async 程式碼，而非序列化的步驟鏈**
序列化的鏈無法表達對話框型與立即型的步驟，也無法在中途做判斷。而序列化唯一的好處是「重新整理後流程仍在」，這在這套設計中反而不是好處：任何導覽都算放棄，重新整理更是。

**為什麼連接器拋錯時把使用者帶離**
那一步的表單多半已經送出，留在上面會讓使用者以為失敗而重按。

**為什麼流程不能套疊**
存檔點只有一格，內層的 `beginFlow` 會蓋掉外層。從 UI 上其實套不進去：流程中途使用者只會在表單頁上，能按的只有那一步自己的取消與送出；會發生的只有一種情況，即連接器在兩步之間跑到非表單的頁面。因此直接拋錯，外層的存檔點完好，內層那個動作由 runner 接住並回報錯誤。

**為什麼流程掛在起點那張表**
頁面只從一個地方取得動作（`use表名Actions`），歸屬規則必須明確，而「起點」是唯一不含糊的說法：跨表的流程從哪張表發起，就掛在哪張表。

**為什麼快速編輯對話框只驗被詢問的欄位、不套用 schema 的 `default`**
不只驗被詢問的欄位的話，沒問到的必填欄位會被算成錯誤。`default` 是新增表單的初始值，修改現有資料時不應冒出來。多筆時不顯示現值，因為那是「填一次、全部改成同一個值」的用法。

**為什麼快速編輯不另開 op 種類**
對每個 id 各跑一次 `store.update`，佇列的合併規則即直接適用。

**為什麼一次要問的欄位放在同一個對話框**
連續動作用於「一步的結果決定下一步」的情況；欄位之間沒有相依時，拆開只是多按幾次確定。

**為什麼對話框是 module-level 的單一實例**
確認框、snackbar 與問欄位的對話框皆與頁面的生滅無關，須能隨時呼叫（動作中、composable 中皆可），因此不經由 provide/inject。與 `notify` 相同的模式：module-level 的狀態加上 `AppShell` 掛一個 `FieldsDialog`，promise 由確定或取消 resolve，整個 App 只有一個實例，再呼叫一次會先把上一個視為取消。`router.afterEach` 會把開著的對話框關閉並 resolve `null`：掛在 `AppShell` 上的對話框會跨路由存活，不關閉的話換頁後它仍開著。

## 搜尋、篩選與排序

**為什麼詳細頁與表單頁不放搜尋**
App Bar 的搜尋表示「這一頁的主體是一份清單」。詳細頁中的子表若需搜尋，應至該表的列表頁進行。

**為什麼篩選在搜尋之前**
篩選抽屜的選項須依整表才能列出「資料中出現過哪些值」，因此使用尚未過濾的那一份；搜尋位於最外層，成本最低（輸入時只重新執行 `includes`）。

**為什麼抽屜開啟時 FAB 須讓開**
FAB 的 z-index 位於 layout 之上，不讓開的話會浮在抽屜上。

**為什麼篩選與排序的抽屜不另外處理互斥**
右側抽屜由兩者共用，一次只顯示一種；抽屜蓋住 App Bar，切換至另一種須先關閉抽屜，因此自然互斥。

**為什麼回到仍帶有搜尋字串的頁面時重新開啟搜尋列**
搜尋欄才會與被過濾的列表一致。

**為什麼搜尋模式下頁籤仍留著**
搜尋與篩選跨所有頁籤，切換頁籤時搜尋字串與條件仍然有效。

**為什麼依狀態切分的頁籤以 `scope` 只留各自的列**
`scope` 位於篩選與搜尋之前，各頁籤只比對各自的部分，各頁籤的資料合起來恰為整張表，合計的工作量與「整張表搜尋一次再切分」相同；若改為各自搜尋整張表再切分，工作量會成為頁籤數的倍數。

**為什麼「共用的列表控制」由外層 provide**
列表本身不需知道自己被放在何處，頁籤頁與儀表板亦不需自行撰寫 provide：拆出的單純列表放進 `TabPage` 或 `DashboardPage`，即自動共用搜尋。

**為什麼不提供多層排序**
手機上幾乎不會使用，且 schema 的 `defaultSort` 已表達「這張表原本的順序」。

**為什麼 `ref` 依名稱、`select` 依選項的先後排序**
`ref` 的值本身為 id，依 id 排序沒有意義；狀態有先後，依字典順序排序並不正確。

**為什麼排序與分組只能擇一**
分組會將原本的順序壓縮為組內的順序，使用者選擇排序後卻只看到每個月份內部重排，容易造成困惑。

## 元件

**為什麼 `DataList` 等列表元件不使用 `RouterLink`**
`RouterLink` 內部有一個讀取 `currentRoute` 的 computed，列表有幾列就有幾個，每次導覽都會全部重算，而這些元件是給上千列的列表使用的。代價是沒有 `router-link-active` 那組 class，列表用不到。

**為什麼 `ViewActions` 的按鈕為原生 `<button>`，而非 `v-btn`**
deck 可能有上千列，`v-btn` 的實例成本較高；且即使未設定 `to`，`v-btn` 仍會呼叫 vue-router 的 `useLink`，開發版中每次導覽都會因此重新計算。

**為什麼 `ViewActions` 的 `menu` 於第一次按下 ⋮ 時才掛上選單**
上千列的列表才不會有上千個 `v-menu` 實例。

**為什麼列表的動作按鈕不放在 `<a>` 之內**
`<a>` 內含互動元素是無效的 HTML。

**為什麼有 `CountLabel` 這個元件，且不使用 `v-chip`**
分組標題與子表區塊的標題須長得一樣。`v-chip` 的內距與行高會跟著外面的標題樣式變化，數字無法置中。標籤的底色以 `on-surface` 疊上透明度，疊在 `bg-surface-light` 的分組標題上也還看得出來。

**為什麼 gallery 沒有圖片時以灰色方塊佔位**
格線才會對齊。

**為什麼 `ViewActions` 在一般頁面不另繪文字按鈕的圖示**
上千列的列表才不會多出同樣數量的 `v-icon`；只有儀表板的窄面板需要它。

**為什麼 `DataCard` 的替代高度不寫死**
各層可以隱藏，卡片的高度差異大。

**為什麼 `ListPage` 不決定每一列的外觀**
每一列的呈現是這張表專屬的部分，由頁面決定。

**為什麼空列表不顯示「找不到資料」**
那是單筆頁面的狀態；空列表就是空的。

**為什麼不使用 `ListPage` 時須自行呼叫 `useListOrder`**
只有頁面知道畫面上的實際排列。

**為什麼表單中的虛擬欄位要先掛上 getter 再計算**
表單編輯的是那一列的普通複本，複製時不可列舉的 getter（`$label`、父列、子列）都不會跟著過來，每次修改欄位也是建立新物件。直接以複本計算，讀父列的虛擬欄位會拿不到資料，因此每次計算前以 `store.withGetters` 重新掛上與快取相同的一套。

**為什麼真實欄位沒有 `readonly`**
顯示上可與虛擬欄位共用同一條唯讀的路，但真實欄位另須自新增與修改的 payload 中排除（否則會蓋掉 Sheet 上的公式），`columnValues`、驗證與預設值各須多一個判斷；目前沒有需求，待需要時再接上。

**為什麼 `ChildList` 的 slot 給整批，而非一次一列**
為了讓 `DataTable` 也放得進來。

**為什麼子表區塊的「展開」是一個頁面，而非就地展開**
換到四件現成的事：返回鍵會回到詳細頁、有頁面的轉場動畫、App Bar 的標題可以是子表的名稱，以及 `ListPage` 會發布這份順序，因此從那裡點進某一筆時，上下一筆走的是同一個父列底下的子列。「展開」不寫筆數，因為筆數已顯示於標題旁的小標籤；也不依是否超過上限而出現或消失，位置固定，使用者不必猜這次有沒有。子表區塊與展開的頁面皆沒有搜尋，子列多到需要搜尋時，應至那張子表自己的列表頁。

**為什麼 `DetailPage` 不支援插在兩個欄位之間**
`DetailPage` 須把欄位切段渲染，`DataDetail` 須能只繪製部分的欄位，為了罕見的需求把兩個元件都變複雜。真的需要時，那一頁不使用 `DetailPage`，以現成的零件自行排列。

**為什麼 `FormPage` 的「找不到這筆資料」使用 `warning`**
網址打錯或資料被刪除都屬於正常的情況，不是錯誤。

**為什麼載入狀態的優先順序為 loading → error → empty**
與資料實際到手的順序一致。`FormPage` 的 loading → loadError → 找不到資料 → 表單亦同。

**為什麼 `PageState` 的 `linear` 不卸載內容，動作失敗也不經過 `PageState`**
同步鈕會重新抓取所有已載入的表，`loading` 再次變為 true；此時若把列表換成進度條，`GroupedList` 的展開狀態會消失，畫面也會整個跳動。`circular` 則為取代，單筆頁面重新抓取時本來就沒有內容可保留。送出失敗、推送失敗等錯誤須讓內容留在畫面上，表單不能消失。

**為什麼 `GroupedList` 的外層不以 `v-if` 包住**
`loading` 一切換便會整個卸載重建，展開狀態隨之消失；同步鈕會重新抓取所有已載入的表，這件事很常發生。

**為什麼 `GroupedList` 的分組內容左右外擴，且 `min-width` 改回 0**
展開與收合的動畫期間，Vuetify 會於 `.v-list-group__items` 暫設 `overflow: hidden`，無法移除（否則尚未展開的內容會溢出）；`v-list` 預設的 `overflow: auto` 亦會裁切往右下的陰影。因此該層以負的 `margin-inline` 外擴、再以 `padding-inline` 抵銷，裁切的範圍便涵蓋陰影。`min-width` 的預設值為 `min-content`，儀表板的窄面板中，展開的子分組會被不換行的標題撐得比面板寬。

**為什麼調整陰影時須一併調整 `--list-card-shadow-extent`，且淡底以 `background-image` 疊上**
分組展開的動畫期間，裁切範圍以它為準，不一併調整的話陰影會被裁切。淡底若以 `background` 簡寫，元件的 scoped 樣式（帶有 `[data-v-…]`，較為具體）會將它蓋掉；淡底不寫成 `:root` 的變數，是因為其值引用 `--v-theme-primary`，寫於 `:root` 會先行求值，頁面中局部切換主題時不會跟著改變。

**為什麼依 `select` 欄位分頁籤時，頁籤直接讀該欄位的 `options`**
不必另外維護一份重複的清單。

**為什麼 `usePanelActive()` 與 `useCurrentTab()` 只接其中一個**
面板外的程式 `inject` 不到面板，面板裡的程式也不知道自己是哪個頁籤，因此依程式所在的位置挑選。

**為什麼 `TabPage` 與 `DashboardPage` 不可互相嵌套**
兩者皆將搜尋登記於 App Bar，列表只會加入最近的一層；兩層各自登記的話，搜尋會互相蓋掉。此外 `TabPage` 將頁籤列登記於 App Bar，儀表板的多個面板無法共用。

**為什麼 `TabPage` 關閉 `v-window` 的 `show-arrows` 與 `touch`**
`show-arrows` 的預設值為 `undefined`，而判斷式為 `showArrows !== false`，不明確關閉的話會在內容上疊一層左右箭頭。`touch` 開啟時可左右滑動切換頁籤，但會與 `DataTable` 的橫向捲動搶手勢；它只綁定觸控事件，電腦上以滑鼠拖曳沒有反應，測試須使用 DevTools 的裝置模擬或實際的觸控裝置。

**為什麼登入頁的 `meta` 兩個都要標**
沒有 `public: true` 的話，登入頁本身會被導向登入頁。

**為什麼登入表單帶 `autocomplete` 並包在 `<form>` 中**
瀏覽器的密碼管理員才會記住並自動填入。

**為什麼離開登入頁時清掉密碼欄**
登入頁會被 KeepAlive 留著，不清的話密碼會一直留在記憶體中。

## 範本

**為什麼佔位字串為 `__table__`**
使用不像英文單字的標記，而非 `template` 這類真實的單字：後者會連 Vue 的 `<template>` 標籤一起被取代，整個頁面便損毀。

**為什麼 `index.html` 的 `<title>` 須另寫一次 App 名稱**
靜態的 HTML 讀不到 TS 中的 `appName`。

## 儀表板

**為什麼手機寬 6 格、電腦寬 24 格**
估算以 1080×1920 的手機與 1920×1080 的電腦螢幕為準。手機的 1080×1920 為實體像素，網頁中約為 360×640 的 CSS 像素（device pixel ratio 為 3）；電腦於縮放 100% 時即為 CSS 像素，`v-container` 的最大寬度為 1400px。

| | 寬的格數 | 每格約（含間距） | 內容區的高度約 | 面板的最小寬度 |
| --- | --- | --- | --- | --- |
| 手機 | 6 | 55px（內容區寬約 330px） | 9.6 格 | 2 格 |
| 電腦 | 24 | 57px（內容區寬約 1368px） | 15 格 | 2 格（約 106px，與手機相近） |

6 與 24 皆可二等分與三等分，24 另可四、六、八等分；兩者為 1:4，手機的半寬（3 格）於電腦上為 12 格。兩者每格的實際大小相近，「高幾格」於手機與電腦上的實際高度亦相近。偏離基準的常見情況，結論不變：較長的手機（例如 20:9，網頁中約 360×800）約 12 格高；開啟 125% 縮放的筆電（網頁中約 1536×864）`v-container` 的最大寬度降為 1000px，每格約 41px，約 16 格高。

**為什麼手機或電腦的排版只由 `useCompactLayout()` 判斷**
JS 與 CSS 依同一個判斷，不會一邊是手機、一邊是電腦。判斷規則只寫在該 composable 中，日後改為依內容區寬度或依裝置時只需修改一處。

**為什麼暫定沿用 Vuetify 的 `mobile`，不使用 `platform`**
`mobile` 依視窗寬度判斷，視窗大小改變時即時更新。`platform` 僅於啟動時比對一次 user agent，且 iPadOS 預設送出 Mac 的 user agent，不適合用於判斷平板。代價是平板直放（例如寬 820px）會被視為手機，6 格時每格約 130px，過大；門檻留待日後調整。

**為什麼手機的自動高度最多 8 格**
16:9 的手機內容區約 9.6 格高，8 格約佔螢幕的 69%；20:9 的手機約 12 格高，8 格約佔 56%。兩者皆低於一個畫面，面板上下總留有空間捲動整頁。內容很少的面板依內容撐開，不會撐到 8 格。

**為什麼電腦的自動大小為寬 8 格、高 7 格，且高度固定**
一個畫面可顯示 3×2 個面板（兩排共 14 格，內容區約 15 格高）。高度固定而非依內容撐開，同一排的面板才會對齊，第二排不致錯落。小外殼約佔一格，內容實際可用約 6 格（1920×1080 時約 340px，deck 約可顯示 4–5 列）。

**為什麼各面板的位置由 JS 計算**
CSS grid 遇到座標重疊時直接讓面板疊在一起，既不警告亦不挪開，因此位置由 `placePanels` 依排版規則算出，CSS 僅照著繪製。

**為什麼窄版的門檻為 3 格以下（寬度小於 200px）**
deck 一列的 4 個圖示按鈕連同內距約 172px，card 約 160px；3 格（手機約 165–180px、電腦約 150–166px）放不下，4 格（約 200px 以上）可容納。手機與電腦每格的大小相近，以同一個門檻涵蓋兩者。container query 僅能使用長度，因此各元件各寫一次 `200px`。

**為什麼部分內容於窄面板中不另外處理**
table 本為檢視完整欄位而用，於面板內橫向捲動即可；gallery 的格線已依寬度減少欄數；圖表以 SVG 繪製，自行縮放；profile 的標題與副標已以刪節號截斷，⋮ 的選單 teleport 至 `body`，可超出面板。deck 窄版時標題與副標上下排列，高度與原本的兩列相近，因此沿用同一個替代高度。

**為什麼窄版的動作列先改為圖示，仍放不下才換行**
每個 `PageAction` 皆有 `icon`，改為圖示即可在不換行的前提下放進較多的動作。

**為什麼「展開」鈕放在各面板的小外殼，而非 App Bar**
未關注的面板亦可直接展開。

**為什麼展開以同一個網址推入一筆 history，而非換到該表自己的頁面**
儀表板的面板未必有對應的獨立頁面，且互動篩出的結果會遺失。網址相同時 KeepAlive 不重建此頁，面板中的狀態皆保留；換頁動畫以 View Transitions 截下前後的畫面，網址相同的展開亦適用，不需另寫動畫。

**為什麼展開與否依 history 的 state 決定，展開鈕只推入 history**
瀏覽器的下一頁會再次展開，自展開的面板進入詳細頁再返回時仍為展開，重新整理後亦維持，不需另外處理這些情況。

**為什麼展開時 App Bar 的標題由儀表板給定**
頁面以元件 import 時讀不到自己 `<route>` 的 `meta.title`，`_ref/` 中的列表亦無路由。

**為什麼互動的選取每張表各記一筆，而非全頁一筆**
選取父列後，再於篩出的子列中選取一筆，父列的選取不會被覆蓋。

**為什麼選取狀態不寫入網址**
儀表板與其他頁面同樣由 KeepAlive 快取，離開後再回來（例如自面板進入編輯頁再返回）仍保留，不需額外處理。

**為什麼父列的選取改變時清除子表的選取**
原本選取的子列可能已不在新的篩選結果中。

**為什麼選取的那一筆被搜尋隱藏時仍保留選取**
子表照樣只顯示它的子列，不因輸入而跳回全部。

**為什麼互動只連動一層**
避免連鎖過深。

**為什麼多選時鎖定其他面板，不使用 `inert`**
`inert` 使整個面板不參與 hit testing，面板自己的捲動可能一併失效，滾輪改為捲動整頁。改以捕獲階段攔下點擊與長按，面板的捲動不受影響。

**為什麼面板只在轉場進行中才命名**
平時帶有 `view-transition-name` 的話，換頁時面板會成為獨立的轉場對象，不隨整個畫面一起滑動。

## 決定不做

評估過而決定不採用的做法，記錄於此以免重複討論；有回頭重新評估時機的，附於條目末尾。只是延後、時候到了就做的項目，仍留在 ROADMAP 的「未完成」。

**路由驅動的通用頁**
即 `src/pages/[table]/` 下的四個通用頁讀取 `schemas[route.params.table]`，新增一張表只需撰寫 schema 並註冊一行。當初的動機是四個頁面檔幾乎相同，而版型元件已將這些樣板抽出，頁面檔剩下的每一行都在說明「這是哪張表、有哪些動作」。再進一步只換得「連四個小檔都不必複製」，而這本來就是 `template/` 的職責；代價則是頁面層失去 Row 型別（版型元件的泛型 slot 便失去作用）、eject 的粒度變為整張表的資料夾（靜態路由段會蓋過動態段），且 schema 開始帶有 UI 設定（`listFields`／`detailTables`）。**回頭重看**：表多至十幾張，而且大多相同。

**佇列持久化**
佇列只存在於記憶體，重新整理、當機、分頁被系統關閉時，未推送的變更會遺失，`beforeunload` 只擋得住主動關閉分頁。單人使用、推送只是一顆按鈕，可以接受。要做的話：存入 `localStorage`（`values` 進入佇列時已序列化，可直接 `JSON.stringify`），流程期間暫停寫入（磁碟上停在流程開始前的狀態，被關閉後再開啟即等於自動回滾）；唯一成本較高的是啟動後須將佇列重新套用至從後端抓回的 `rows`，需要一個只處理部分欄位的 `coerceRow`。**回頭重看**：確實遺失過一次未推送的變更。

**離線寫入佇列**
即離線時照常操作、連線後再送出。需要 IndexedDB、寫入佇列與衝突處理一整套，成本結構與佇列持久化相同，而且多了「離線期間看到的資料可能已經過期」的問題。**回頭重看**：確實經常於沒有網路的地方使用。

**推送失敗的逐筆補償**
即記錄哪幾筆已成功、只重送失敗的部分。推送為全有全無，不會有「成功了幾筆」的情況；而且 id 由前端發、`create` 定義為冪等，整批重送本來就是安全的。

**衝突時將佇列重新套用至新資料**
即衝突時保留未推送的改動，套用至重新抓回的資料上。成本與佇列持久化相同；衝突時的兩條出路（放棄並重抓、強制推送）已足夠。

**連續動作中返回即回到上一步，而非整條取消**
代價是三件事加起來等於一個多頁精靈：每一步改為 `push`，且結束後須清除歷史；存檔點須由一格變為一疊（每一步可單獨收回）；上一步的表單須帶著使用者上次填寫的值重新開啟。**回頭重看**：確實有三步以上、經常需要回頭修改的流程。

**編輯表單的預設值通道**
`useEditForm` 不讀取 `navigationDefaults()`，因此編輯表單可以作為流程的一步，但無法將上一步的結果預先填入。目前想不到需要的情境。

**連續動作的進度指示**
即「第 1 步／共 2 步」。流程頂多兩三步，每一步皆為完整的一頁，App Bar 上有自己的標題。

## 已知的權宜作法

目前採用、但已知並不理想的做法。這些不是待辦。

**`refTable` 沒有型別檢查**
只存代稱字串，不保證確實存在於 `schemas`。為了避免 `schema/types.ts` 反過來 import `schema/index.ts` 造成循環依賴，目前接受這個缺口。

**`template/` 不在 `src/` 底下**
因此不會被 lint 與型別檢查掃到，元件的 props 改變時範本不會自動報錯。目前以「將範本複製為一張暫時的表、建置通過後再刪除」的方式手動驗證。

**刪除時會閃一下「找不到這筆資料」**
快取更新之後、返回動畫進行期間，詳細頁的 row 已為 null。那筆資料確實已不存在，語意上可以接受，因此不為此增加凍結顯示的機制。
