# 設計取捨

各份文件只寫已確定的規則。採用某種做法、不採用另一種做法的理由，集中記錄於此，供維護框架時參考。

- 依主題分節，各節的條目大致依對應文件的順序排列
- 最後兩節為評估後決定不做的項目，以及已知的權宜作法

## 架構與頁面

**為什麼頁面仍為手寫**
每張表的顯示方式差異大，還有跨表組合的頁面，無法由 schema 產生。重複的部分以元件庫、composables 與頁面範本減少。

**為什麼 KeepAlive 的 key 帶有完整網址**
不帶完整網址時，同一個路由換 id（`/表名/A` → `/表名/B`）對 Vue 而言是同一個元件、同一個 vnode，會就地更新。頁面須自行隨 id 重新載入，各列的元件狀態也無法分開保留。帶有完整網址後，一個實例只對應一個網址，路由參數對該實例而言是常數。

代價是 KeepAlive 從「每個元件一份」變為「每個網址一份」，因此須以 `max` 限制數量。連續切換超過 50 列而不回到列表時，列表頁被擠出快取，展開狀態隨之消失。

**為什麼被快取的頁面仍在運作，以及 KeepAlive 的規則由此而來**
KeepAlive 的 `deactivate` 只搬移 DOM，不暫停元件的 effect。`onDeactivated` 於渲染之後才執行，比 pre-flush 的 `watch` 還晚。因此外面已經換頁，被快取的頁面仍會因外部的變化重新計算、重新渲染。

- 舊的換頁動畫中，離場的頁面是活的 DOM，直接造成「短暫閃現錯誤的內容」
- 改用 View Transitions 後，離場的一側為截圖，不再看得到這個問題。但頁面回到畫面時，仍帶著背景期間算出的狀態
- 流入被快取頁面的資料只有兩種：路由參數（讀取一次即固定）與共用快取（任其改變）

各條規則的理由：

- `[id]` 頁面不隨路由變化：離開中的頁面會讀到目的地的 id
- 快取改變時任其改變：資料確實被刪除時，顯示「找不到這筆資料」即為正確的結果
- 新增頁於 `onActivated` 重建表單：網址固定，不重建時表單停留在上次的內容，也讀不到新的預設值。編輯頁「離開後再回到同一列」也是同一份實例，不重置時，上次未儲存的輸入仍在，容易被誤存
- Teleport 出去的浮動元件自行處理進場與出場：否則離開的頁面會把按鈕留在畫面上
- 列表載入中時，不以 `v-if` 整個替換：同步按鈕重新抓取所有已載入的表，每次都會卸載重建，`GroupedList` 的展開狀態隨之消失
- 捲動位置另外記錄：KeepAlive 保留的是元件，視窗的捲動位於元件之外

**為什麼換頁動畫使用 View Transitions，不使用 `<Transition>`**
`<Transition>` 須看到新舊兩個不同的元件才會播放。儀表板的展開與縮回網址不變，KeepAlive 的 key 相同，前後是同一個元件，`<Transition>` 無從觸發。View Transitions 由瀏覽器截下 DOM 更新前後的畫面再播放動畫，不論前後是否為同一個元件。因此換頁與展開共用同一套動畫。

- **導覽失敗時略過動畫**：畫面沒有改變，滑動兩張相同的截圖沒有意義
- **滑動整個畫面（`root`）的截圖，不為內容區命名**：`root` 的截圖即為當時看到的畫面，不受捲動位置影響。單獨為內容區命名時，元素的位置隨捲動改變，截圖於動畫中會上下跳動
- **舊做法（`<Transition>` + `<KeepAlive>`）的兩個限制**，改用 View Transitions 後皆不復存在：
  - 離場的一側套用的是該 vnode 上次啟用時的 transition hooks，方向須改以屬性選擇器讀取
  - 頁面的 root 須為單一元素，因此三個版型都在外層包一個 `div`。這個 `div` 目前仍保留

**為什麼 App Bar 的動作經由 provide／inject，FAB 與 `RecordNav` 經由 Teleport**
- App Bar 屬於 `AppShell`，頁面只須把動作交給 `AppShell`，無須實際搬移 DOM
- FAB 與 `RecordNav` 的箭頭為 `position: fixed`。置於頁面中時，帶有 `transform` 或 containment 的祖先（例如儀表板的面板）會成為定位的基準，按鈕便不再貼齊螢幕。因此兩者送至 `body`
- 換頁動畫中，三者皆另有 `view-transition-name`，不隨頁面滑動

**為什麼三個登記處皆只採用一個頁面的內容**
App Bar 的動作、底部動作列與 FAB 皆經由同一個 `registerActions`（`useActionSlot.ts`），同一時間只採用一個頁面的動作。因此須以 `isActive` 擋下被 KeepAlive 快取的頁面：這些頁面仍在全速運作，其動作一旦改變，便會覆蓋目前頁面的動作。

**為什麼表單的按鈕在螢幕最底端**
「取消」與「送出」始終位於拇指可及之處，無須把長表單捲到最後才能按到。表單本來就是「按下才算完成」的頁面，此時不應讓使用者分心切換頁面，因此按鈕直接取代底部導覽列。

**為什麼完成動作後以 `leaveAfterAction` 離開，不使用 `router.push`**
使用 `push` 會把已完成任務的表單頁留在歷史中，按上一頁又回到該頁。編輯頁會是舊的表單，刪除後的詳細頁更是已不存在的資料。

**為什麼取消按鈕本身不詢問是否離開**
取消按鈕觸發的導覽會經過 `useLeaveGuard`。取消按鈕若自己再詢問一次，使用者會被問兩次。

**為什麼連續動作的第二步起一律詢問**
這張表單可能尚未填寫任何內容，但前面的步驟已寫入資料，離開即等於收回整條流程。

**為什麼 `detailOrder` 與 `formOrder` 分開**
詳細頁與表單頁的需求不一定相同。

## 資料表與 schema

**為什麼以 `TableSchema<Row>` 宣告**
TS 因此能檢查 schema：
- `key`、`labelColumn`、`searchable`、`sortable`、`detailOrder`、`defaultSort` 只能填入 Row 擁有的欄位名稱
- `type` 須與該欄位的值型別相符
- 虛擬欄位 `value` 的參數直接為該表的 Row

**為什麼不以 row number 作為主鍵**
排序、刪除、插入都會使 row index 位移。

**為什麼主鍵是一般欄位上的標記，不是獨立的系統欄位**
- 與父表共用 id 的一對一延伸表，須以 `ref` 作為主鍵
- 商品編號這類自然鍵，須由使用者輸入
- 兩者都要求主鍵能像一般欄位一樣，出現在表單、詳細頁與搜尋中

標記的形式與 `labelColumn` 相同，`row.id` 與該欄恆等。store、路由與關聯照舊只讀取 `row.id`。主鍵建立後不能修改，因此兩者不會不同步。

**為什麼主鍵建立後不能修改**
主鍵一修改，以下各處都記著舊 id，須全部連帶更新：子列的 ref、待推送佇列（推送前後端仍為舊 id）、詳細頁的網址、KeepAlive 的快取、列表順序與選取。可修改的 id 留待確實需要時再做，見 ROADMAP 的「未完成」。

**為什麼主鍵的唯讀由呼叫端判斷，store 另外再檢查**
新增與編輯共用同一份 `formOrder`。新增時要填寫的主鍵必然出現在編輯表單中，設計者無法只從編輯表單拿掉。因此表單依「是否修改既有的列」自動將主鍵設為唯讀：
- `FormPage` 依列是否已有 `id` 判斷
- `askFields` 依是否提供 `rows` 判斷

`setFieldAction` 這類不經過表單的寫入，由 store 的 `update` 作為最後一道防線。

**為什麼 `create` 擋下重複的 id 與剛刪除的 id**
- 後端把已存在的 id 視為重送，直接略過。使用者輸入重複的編號時，那一列會被無聲地吞掉，因此須在前端寫入前擋下
- 剛刪除、尚未推送的 id 若再新增，佇列會把刪除與新增合併為一筆新增。Sheet 上的舊列仍在，新增同樣會被略過。因此須推送之後才能再使用該 id

**為什麼主鍵不以 `'` 開頭**
`'` 是 Sheet 的純文字前綴，存入後不屬於內容。`'A1` 讀回即為 `A1`，與前端記錄的 id 不同，因此找不到該列。

**為什麼主鍵只能使用 `encodeURIComponent` 不會改變的字元**
主鍵直接接進網址（`/表/id`），沒有編碼：
- `/` 與 `\` 被視為路徑分隔
- `?` 與 `#` 之後變成查詢字串或錨點
- `%xx` 被 vue-router 解碼成其他字元

改為組網址時編碼，雖然可容許任何字元，但框架、範本與各頁面約二十處組網址的地方都須改用同一個函數，日後新寫的頁面也容易遺漏。主鍵多為英數編號，因此選擇限制字元，代價是主鍵不能有中文與空白。

`.` 與 `..` 能通過這項檢查。但即使編碼成 `%2E`，瀏覽器依網址規範仍將其視為「目前這層」與「上一層」，因此只能擋下。

**為什麼 `update` 不把主鍵寫回 Sheet**
值沒有改變，寫回只是多一格無意義的寫入。後端也因此無須處理「更新主鍵那一格」的情況。

**為什麼表頭使用對外的名稱**
使用者可直接開啟 Sheet 檢查或手動修改資料。程式中另用 `key`：英文、容易輸入，且不會改變。

**為什麼只有部分型別加上單引號**
- `number` 與 `date` 不加：這兩種本來就應讓 Sheet 存為數字與日期，Sheet 上的 `SUM` 與日期格式才能使用
- `duration` 不加：實測不會被 Sheet 改寫
- `ref` 不加：
  - `ref` 的值是父列的 id，必須與主鍵完全相同
  - 主鍵本身不能加單引號：後端須以 id 與 Sheet 上的顯示值比對，才找得到那一列
  - 兩邊的規則一致才不會脫鉤。只有一邊加時，`row.欄位 === 對方.id` 不相等，關聯無聲地斷掉
- 主鍵不以數字或 `=`、`+`、`-` 開頭，也不含 `/`：否則會被 Sheet 解析為數字、公式或日期而找不到列。這也使主鍵不會符合任何須加單引號的形狀，`text` 型別的主鍵因此同樣不加
- 只有前端能做這件事：後端只認得表頭，分不出「文字欄位中的 `0912`」與「數字欄位中的 `0.5`」

**為什麼 `date` 讀入時歸零至午夜**
Sheet 上手動加了時間時，「看起來相同的兩列」排序或篩選的結果才不會不同。

**為什麼 `duration` 是「時:分:秒」的字串**
- Sheet 上即為 `2:30:00`，開啟時看得懂
- 表單使用一般的文字框：原生的 `type="time"` 容不下超過 24 小時的值
- 排序與篩選換算為秒，`9:30:00` 才不會排到 `10:00:00` 後面
- `duration` 不兼作時間點：它沒有上限，也沒有上午與下午的概念

**為什麼 `boolean` 的空值維持空，不視為否**
「尚未決定」與「否」是兩件事，空值視為否會把前者無聲地改成後者。空值也使 `required` 仍有意義。

**為什麼 `boolean` 在 Sheet 上不使用核取方塊，在表單中不使用開關或勾選框**
核取方塊、開關與勾選框都只有兩種狀態，無法表示空值。因此 Sheet 上直接存 `TRUE`、`FALSE` 或空白。表單則使用兩個互斥的按鈕，再按一次即回到空值。

**為什麼 `formatColumnValue` 以參數區分顯示與寫回 Sheet**
- 兩者大多相同，只有 `boolean`（是／否與 `TRUE`／`FALSE`）和 `ref`（父列的名稱與 id）不同
- 集中在同一個函數中分支，無須另外維護一份寫回用的格式化
- `ref` 原本寫回 id，只是因為送進 `serializeRow` 的值沒有掛 getter、取不到父列。明確指定寫回模式後，即使傳入掛了 getter 的列，也一律寫入 id

**為什麼 `boolean` 寫回 `TRUE`／`FALSE`，不寫顯示的「是」「否」**
Sheet 把 `TRUE`、`FALSE` 解析為布林值，讀回時的顯示值仍為 `TRUE`、`FALSE`。寫入「是」「否」則只是文字，換了語言或格式就對不上。

**為什麼 Drive 的圖片使用縮圖網址**
縮圖網址沿用瀏覽器已登入的 Google 帳號，無須經過後端，也沒有 CORS 的問題。

**為什麼虛擬欄位與 `columns` 分開放置**
`coerceRow`、`serializeRow` 與表單因此完全無須知道虛擬欄位的存在。

**為什麼列上的 getter 不可列舉**
寫回後端時才不會誤送。

**為什麼跨表的值是 getter，不在父表另存一份**
- 雙向維護容易不一致，例如新增子列時須記得更新父列。Sheet 上也會多出無人維護的欄位
- 改為讀取時計算，資料來源永遠只有一份，新增或刪除子列也無須維護任何東西
- 代價是載入一張表時，須一起載入它的父表與子表，列上的 getter 才有資料可讀。以目前的規模沒有影響，而顯示關聯資料本來就須載入整張表

**為什麼子列建立索引**
`$子表_欄位key` 若每次讀取都重新掃描整張子表，一個列表頁每一列讀取好幾次，即為 N×M 次比對。

改為每條關聯一份「父列 id → 子列」的索引：
- 整張子表排序一次後分組，放在 `computed` 中
- 子表的陣列被替換時才重建，讀取只是查表
- 回傳的陣列因此保持同一個參照

**為什麼子列 getter 的名稱帶有欄位名稱**
無須任何設定，看 schema 即可推得名稱。同一張子表有兩個 ref 指向同一張父表時，兩條關聯各有各的名稱。

**為什麼快速編輯的打字類欄位在失焦時才寫入**
每輸入一個字就寫入時，佇列與快取隨每次按鍵更新。未完成的值（打到一半的日期、數字）也會被驗證擋下，不斷出現錯誤。選項、是非與日期是一次選定的值，沒有「輸入到一半」的狀態，因此一修改就寫入。

**為什麼快速編輯驗證不通過時保留輸入的內容，不還原**
還原會無聲地丟棄使用者剛輸入的內容，使用者也看不出哪裡錯了。保留內容並在欄位下方顯示錯誤，使用者可以直接修正。

**為什麼快速編輯的欄位由頁面指定，不寫在 schema**
哪些欄位適合隨手修改，取決於這一頁的用途。同一張表在不同頁面（例如 dashboard 的小面板）可能不同。這與 `order` 相同，由頁面的 prop 決定。

**為什麼頁面的 `order` 是覆寫，預設仍留在 schema**
未指定的頁面、`askFields` 與 dashboard 的面板，都須有一份欄位順序可用。全部搬到頁面時，每一頁都須自行撰寫一份。

這與 `defineView` 的 view 不同：view 只決定一列的欄位擺在版面的哪個位置，`order` 決定的是整頁的欄位集合。AppSheet 把這些設定掛在 view 上，因此一張表能有多個 view。此處以頁面的選用 prop 達到相同的效果。

**為什麼條件式格式寫在表層級，不寫在欄位上**
同一個條件常須同時標示多欄，例如逾期時標題與日期都變紅。寫在表層級時，條件只寫一次，以 `columns` 列出套用的欄位。

**為什麼條件式格式另以 `displayValue` 算出，不讓 `formatColumnValue` 一起回傳**
- `formatColumnValue` 的字串另有寫回 Sheet、搜尋與 `$label` 等用途，改為回傳物件會影響這些地方
- 規則寫在表層級，`formatColumnValue` 只取得欄位，取不到 schema

因此另包一層顯示專用的函數。顯示值的三條路徑（view、`DataDetail`、`DataTable`）都改用此函數，文字與格式一起往下傳，每個位置只指定一次。

**為什麼條件式格式的顏色是常用色名，不是語意色**
設計者要表達的多半是「紅色」「綠色」這類具體的顏色。Vuetify 的 `error`、`success` 等語意色只有少數幾種，且多半深淺色主題共用一個色值。

- 每個色名各有淺色與深色主題的兩組色值，避免深藍在黑底上看不清楚
- 色值取自 Material Design 色板，以 APCA 檢查。WCAG 2 的對比公式會高估深色主題中紅色的可讀性
- 黃色在白底上，色板中沒有任何一個能達到小字的門檻，較深的黃又已偏橘。因此淺色主題的黃，取深色主題那個黃的色相，以 OKLCH 降低亮度直到達標。OKLCH 的色相依人眼的感知計算，調暗後仍看得出是同一個黃

**為什麼共用色名登記為 Vuetify 的主題色，並加上 `vuesheet-` 前綴**
- 登記為主題色後，Vuetify 自動產生 `text-`、`bg-`、`border-` 的 class 與 CSS 變數，元件的 `color` prop 也能直接使用，並隨深淺色主題切換，無須為深色主題另寫一套選擇器
- 原本寫在 `FormattedValue` 中的 class，只有該元件能使用
- Vuetify 預設載入的 Material 色板已佔用 `text-red` 等名稱，且為固定色值、不隨主題切換。同名的 class 會因載入順序而互相覆蓋，因此加上前綴
- 色值直接引用 `vuetify/util/colors` 的色板，不另外抄寫色號

**為什麼多條規則符合時，顏色取第一個、字形取聯集、圖示全取**
- 一段文字只能有一種顏色，以宣告的順序決定優先
- 粗體、底線等可以同時成立，任一條規則要求即套用
- 每個圖示各自代表一個條件，全部列出才不會遺漏

**為什麼 `showIf` 寫在欄位上，且只作用於詳細頁**
欄位是否有意義，多半取決於這一列的資料本身，例如取消原因只在已取消的那幾列有意義，與頁面無關。因此 `showIf` 與 `required`、`validate` 同樣寫在欄位上。

表單若也隱藏欄位，須另外決定：被隱藏的必填欄位是否仍須驗證、已有的值保留或清空。目前沒有這個需要。

**為什麼 `onEmpty` 只在子列減少時檢查，不維持「父列必有子列」**
父列常須先建立，再新增子列，例如先新增訂單，再帶著它的 id 新增明細。兩步之間，父列必然沒有子列。若把「沒有子列」當成隨時成立的約束，這個流程便無法進行。

只在子列被刪除或改指他處的那一刻檢查，即可涵蓋「最後一列子列離開」的情況，而不影響建立。刪除與改指他處同樣是子列減少，因此不分成兩個設定。

**為什麼虛擬的 `ref` 不進入關聯圖**
- 反向的 `$子表_欄位key` 須對子表的每一列計算虛擬值才能建立索引，且使用父表時就須連帶載入子表
- 連帶刪除沒有意義：虛擬欄位不在 Sheet 上，指向關係由另一列父列決定
- 目前只需要正向的 `$欄位key`，反向留待確實需要時再加。屆時關聯圖的每個使用處都須分辨虛擬的關聯，並將其排除於連帶刪除之外

**為什麼合法性驗證只在前端**
Sheet 本來就能手動開啟修改，後端檢查合法性也擋不完整，因此把這份責任明確劃給前端。

後端只保留結構完整性：寫錯的欄位名稱會直接在 Sheet 上產生一欄新的表頭，或寫錯儲存格，這一項不能省略。新增表單的初始值同理，只存在於前端，後端不為未提供的欄位填入任何值。

**為什麼 store 的 `create`／`update` 再驗證一次**
擋下繞過表單的程式錯誤。

**為什麼 `schema/` 根目錄只放純函數**
純函數不使用 reactivity，store、元件與 composable 皆可直接呼叫。反應式的包裝另外置於 `composables/data/`。

**為什麼 `allowCustom` 與 `suggestedValues` 分開**
「清單自行增長」不一定是好事：輸入錯誤的值也會變成建議，而清單只會變長、不會收回。因此「允許自填」與「建議的來源」分開，由設計者自行決定。

**為什麼建議值是函數，不是「從資料帶出」的開關**
建議的來源不只一種：這張表用過的值、同一個父列的其他子列的值、其他表的值。開關只能表達第一種。函數接收掛了 getter 的列與整張表，三種都寫得出來，原本的開關也只是其中一行。

**為什麼分組的 `sortKey` 與 `label` 分開**
依顯示的字串排序會出錯，例如「10月」排在「2月」前面。

**為什麼 `TableSchema<Row>` 只做單向的檢查**
Row 介面仍須手寫，包括虛擬欄位的 `readonly xxx`，以及 store 掛上的 `readonly $欄位key?`。泛型不會反過來從 schema 產生介面：那須要兩段式的 builder 加上跨表的延遲查表，schema 便不再是一眼可看完的物件字面值，不值得。

框架端一律使用不帶參數的 `TableSchema`，其 Row 預設為 `any`。不使用 `object`：`keyof Row` 會使 TS 將 Row 判為逆變，`TableSchema<XxxRow>` 將無法指派給 `TableSchema<object>`。

**為什麼預設值經由 `history.state`，不使用 query param**
值不出現在網址上。與全域變數相比，**值綁在那一筆歷史紀錄上**，不會殘留下來影響之後無關的表單。

## 資料流與佇列

**為什麼沒有「只重抓一張表」的 API**
store 會自行補齊快取，頁面沒有須自行補資料的時機。

**為什麼表單一律送出整列**
payload 較大，但省去在表單中比對原始值的複雜度。

**為什麼新增的 id 由前端發號**
重送因此變得安全：`create` 的語意為「id 不存在即建立，已存在即視為已完成」，整批重送無須記錄哪幾列已成功。後端仍須阻擋重複的 id，因為 Sheet 可以手動開啟修改。

**為什麼推送不回傳資料列**
寫入時前端的快取已修改好，推送成功後 `refresh()` 本來就會重新抓取。

**為什麼同步按鈕在推送失敗時不重抓，且重抓的範圍包括載入失敗的表**
- 推送失敗後重抓，會無聲地覆蓋未推送的變更
- 載入失敗的表不在快取中。不另外計入時，第一次就載入失敗的表，按同步也不會再試
- 同步按鈕同時也是重新整理，因此平時一律可按

**為什麼表單開啟時停用同步**
避免修改到一半的內容被同步的結果覆蓋。

**為什麼同步按鈕不經過 `useAppBarActions`**
那條管道供頁面登記動作使用。同步按鈕混入時，會把頁面的動作擠進 ⋮ 選單。

**為什麼快取不分「已送出」與「未送出」**
畫面不應關心一列是否已送出，只須顯示使用者眼中的現況。須分辨的是 `pending`，那是 `flush` 的責任。跨表算出的值（例如父表顯示子列的加總）讀取同一份共用資料，會自動重算，無須任何跨表的失效機制。

**為什麼佇列存放序列化後的字串，不存放 `Partial<Row>`**
- 那本來就是要送給後端的形狀，`flush` 取得後即可送出
- 其中沒有 `Date` 物件，日後要存入 `localStorage` 時，可直接使用 `JSON.stringify`，無須回頭修改資料結構

**為什麼存檔點存整張表，不逐列存放**
流程進行中沒有其他寫入者：使用者正在填寫表單，而 `flush()` 於流程進行中被擋下。若不擋下，按了同步就會把半成品推進 Sheet，之後無法回滾，存檔點只能還原記憶體。

因此整張還原與逐列還原等價，但簡單許多：`patch` 本來就替換整個陣列，佇列的 `PendingOp` 也一律建立新物件、不就地修改，淺層複製即足夠。

**為什麼存檔點是隱式的（store 中的環境狀態）**
流程期間的寫入不是流程的程式做的，而是表單頁做的。`useCreateForm` 與流程的程式隔著一次導覽，是不同的元件，取不到明確傳下去的交易物件，函數也無法放進 `history.state`。因此 `activeFlow` 放在 store 中，由 `store.create`、`update` 自行查看。

**為什麼假後端與真後端回傳相同的形狀**
上線時只須於 `.env` 填入一個網址，`appScript.ts` 以外的程式皆無須修改。因此假後端也與真正的 Sheet 一樣，只存放原始字串，型別轉換同樣交給呼叫端的 `coerceRow`。

## 動作

**為什麼所有動作使用同一種描述**
同一個動作可以直接移到另一個位置，無須修改。

**為什麼 `icon` 一律須提供**
底部動作列雖然只顯示文字，但形狀統一後，同一個動作移到其他位置時無須補上任何內容。

**為什麼 `PageAction` 只有 `onClick`，沒有宣告式的 `to`**
- 求值的時機：動作物件在頁面 setup 時即建立，寫進 `to` 的值那時就已固定。切換頁籤後再按新增，會帶入舊的狀態
- 統一為一種，也避免兩者都設定時，「導覽」與「執行」兩件事同時發生
- 代價是動作呈現為 `<button>`，不是 `<a>`，失去中鍵開新分頁與連結的無障礙語意。此框架的動作大多位於 FAB 與 App Bar，影響不大

**為什麼 ref 欄位的那一格是按鈕，不是連結**
從 `<RouterLink>` 改為 `<button>` 後，中鍵開新分頁的功能消失，與 `PageAction` 沒有 `to` 是同一個取捨。導覽使用 `push`，返回時詳細頁仍在。

**為什麼欄位動作不是內建的**
前往 ref 的父列，與開啟網址、改為今天一樣，都是 builder。需要就列入，不需要就不列，不設「空陣列表示內建」這種第三種狀態。

**為什麼 `confirm` 是宣告式，`askFields` 不是**
`confirm` 對每個動作都相同，動作本體無須知道結果，因此做成語法糖。`askFields` 的結果是動作要拿去使用的，只能在 `onClick` 中自行 `await`。

**為什麼 builder 是一般函數，不是 composable**
同一個 builder 須用於詳細頁目前那一列（會變動的 Ref）、欄位動作，以及列表的每一列（view 的 `actions`）。

- 若 builder 本身為 composable（接收 Ref、回傳 computed），每一列每次求值都會建立一個 computed，也違反 composable 只在 setup 中呼叫的慣例
- 改為一般函數後，每次呼叫只建立一個一般物件
- 只有交給 FAB 與 App Bar 的那一層須隨資料更新，由 `useAction`、`useRowAction` 負責

**為什麼以列為參數的動作由頁面綁定，不由 `use表名Actions` 綁定**
「綁定至目前那一列」只在詳細頁成立，列表的每一列則各自呼叫。若由 `use表名Actions` 負責綁定，它便須知道自己供哪一種頁面使用，列表也無法取得可逐列呼叫的版本，同一個動作勢必定義兩份。因此 `use表名Actions` 只負責定義，綁定交由需要的頁面以 `useRowAction` 處理。

**為什麼刪除後自動離開**
「刪除目前顯示的那一列後離開該頁」在任何頁面皆成立，不應要求每個詳細頁各自傳入 `leaveAfterAction`。由頁面傳入時，漏傳仍可通過編譯，刪除後卻停留在「找不到這筆資料」的畫面。因此 `deleteAction` 於刪除後檢查目前的路由是否為該列的詳細頁，是則自動離開。`onDone` 只用於其他額外的處理。

**為什麼 `use表名Actions` 的每一項是單一動作，不是陣列**
一個位置放置哪些動作由頁面決定，因此由頁面組成陣列，例如 `[editAction.value, deleteAction.value]`。不適用的動作以 `null` 表示，由接收的位置略過。`null` 的處理集中於框架的幾個位置元件中，頁面與 `use表名Actions` 都無須判斷。

早期的 builder 一律回傳 `ComputedRef<PageAction[]>`，以空陣列表示不適用。這使單一動作也須包成陣列，陣列的名稱也與內容（只有一個動作）不一致。

**為什麼動作屬於其所在資料的那張表，且各表的動作不互相呼叫**
- 與 AppSheet 相同，設計時先想的是「這一頁、這個區塊要有哪些按鈕」，因此動作跟著畫面上的資料：詳細頁的動作屬於那一頁的表，子表區塊屬於子表
- 各表的 `use表名Actions` 不呼叫彼此，維護即以表為單位，修改一張表不會牽動另一張
- 跨表的需求經由 ref 的 getter 讀取資料，再以內建 builder 組出。寧可重複幾行，也不在表與表之間建立共用的函數

**為什麼 `null` 由繪製按鈕的元件處理，不由中間層處理**
不同位置對 `null` 的解讀不同：FAB、App Bar、子表區塊、deck、profile 與 gallery 略過 `null`，card 與詳細頁的標頭則把它當成空格、保留位置。只有最後繪製按鈕的元件知道 `null` 在該處代表什麼。若於版面元件或登記機制等中間層統一過濾，空格的資訊便會遺失。

**為什麼流程的第一步使用 `push`，之後使用 `replace`**
- `push` 保留發起流程的那一頁，`replace` 使完成的表單不留在歷史中
- 結果是歷史始終只有「起點 → 目前這一步」兩筆：任何一步按返回或取消都回到起點，流程結束後也能從終點返回起點
- 全部使用 `replace` 時，起點會被第一步取代，取消時便無處可去

**為什麼流程是 async 程式，不是序列化的步驟鏈**
序列化的步驟鏈無法表達對話框型與立即型的步驟，也無法在中途判斷。序列化唯一的好處是「重新整理後流程仍在」，這在此設計中反而不是好處：任何導覽都視為放棄，重新整理更是如此。

**為什麼流程的程式拋出錯誤時，把使用者帶離目前的頁面**
那一步的表單多半已經送出，留在該頁會使使用者以為失敗而重按。

**為什麼流程不能套疊**
存檔點只有一格，內層的 `beginFlow` 會覆蓋外層的存檔點。

從 UI 上其實套不進去：流程中途使用者只會在表單頁上，能按的只有那一步自己的取消與送出。會發生的只有一種情況：流程的程式在兩步之間前往非表單的頁面。因此直接拋出錯誤，外層的存檔點完好，內層的那個動作由 runner 接住並回報錯誤。

**為什麼流程定義於起點那張表**
頁面只從一個地方取得動作（`use表名Actions`），歸屬規則須明確，而「起點」是唯一不含糊的說法：跨表的流程從哪張表發起，就定義於哪張表。

**為什麼快速編輯對話框只驗證被詢問的欄位，不套用 schema 的 `default`**
- 不只驗證被詢問的欄位時，未詢問的必填欄位會被算成錯誤
- `default` 是新增表單的初始值，修改現有資料時不應出現
- 多列時不顯示目前的值，因為那是「填一次，全部改成同一個值」的用法

**為什麼快速編輯不另外新增操作的種類**
對每個 id 各執行一次 `store.update`，佇列的合併規則即直接適用。

**為什麼一次要詢問的欄位放在同一個對話框**
連續動作用於「一步的結果決定下一步」的情況。欄位之間沒有相依時，拆開只是多按幾次確定。

**為什麼對話框是 module 層級的單一實例**
確認框、snackbar 與詢問欄位的對話框皆與頁面的建立與銷毀無關，須能隨時呼叫（動作中、composable 中皆可），因此不經過 provide／inject。

- 模式與 `notify` 相同：module 層級的狀態，加上 `AppShell` 掛載一個 `FieldsDialog`
- promise 於確定或取消時 resolve。整個 App 只有一個實例，再呼叫一次時，先把上一個視為取消
- `router.afterEach` 關閉開啟中的對話框，並 resolve `null`：掛在 `AppShell` 上的對話框跨路由存在，不關閉時，換頁後它仍開著

## 搜尋、篩選與排序

**為什麼詳細頁與表單頁不放置搜尋**
App Bar 的搜尋表示「這一頁的主體是一份清單」。詳細頁中的子表若須搜尋，應至子表的列表頁進行。

**為什麼篩選在搜尋之前**
- 篩選抽屜的選項須依整張表，才能列出「資料中出現過哪些值」，因此使用尚未過濾的那一份
- 搜尋位於最外層，成本最低，輸入時只重新執行 `includes`

**為什麼抽屜開啟時 FAB 須讓開**
FAB 的 z-index 位於 layout 之上，不讓開時會浮在抽屜上。

**為什麼篩選與排序的抽屜不另外處理互斥**
右側抽屜由兩者共用，一次只顯示一種。抽屜蓋住 App Bar，切換至另一種須先關閉抽屜，因此自然互斥。

**為什麼回到仍帶有搜尋字串的頁面時，重新開啟搜尋列**
搜尋欄才會與被過濾的列表一致。

**為什麼搜尋模式下頁籤仍保留**
搜尋與篩選跨所有頁籤，切換頁籤時，搜尋字串與條件仍然有效。

**為什麼依狀態切分的頁籤以 `scope` 只保留各自的列**
`scope` 位於篩選與搜尋之前，各頁籤只比對各自的部分。各頁籤的資料合起來恰為整張表，合計的工作量與「整張表搜尋一次再切分」相同。若改為各自搜尋整張表再切分，工作量會成為頁籤數的倍數。

**為什麼共用的列表控制由外層 provide**
列表本身無須知道自己置於何處，頁籤頁與儀表板也無須自行撰寫 provide：拆出的單純列表放進 `TabPage` 或 `DashboardPage`，即自動共用搜尋。

**為什麼不提供多層排序**
手機上幾乎不會使用，schema 的 `defaultSort` 也已表達「這張表原本的順序」。

**為什麼 `ref` 依名稱、`select` 依選項的先後排序**
`ref` 的值本身為 id，依 id 排序沒有意義。狀態有先後，依字典順序排序並不正確。

**為什麼排序與分組只能擇一**
分組會把原本的順序壓縮為組內的順序。使用者選擇排序後，卻只看到每個月份內部重排，容易造成困惑。

## 元件

**為什麼 `DataList` 等列表元件不使用 `RouterLink`**
`RouterLink` 內部有一個讀取 `currentRoute` 的 computed。列表有幾列就有幾個，每次導覽都全部重算，而這些元件供上千列的列表使用。代價是沒有 `router-link-active` 這組 class，列表用不到。

**為什麼 `ViewActions` 的按鈕為原生 `<button>`，不是 `v-btn`**
- deck 可能有上千列，`v-btn` 的實例成本較高
- 即使未設定 `to`，`v-btn` 仍會呼叫 vue-router 的 `useLink`，開發版中每次導覽都因此重新計算

**為什麼 `ViewActions` 的 `menu` 於第一次按下 ⋮ 時才掛上選單**
上千列的列表才不會有上千個 `v-menu` 實例。

**為什麼表格的欄寬只有三種設定，不填寫數字**
固定的數字換一個螢幕寬度就不合用。設計者真正要表達的是三種意圖：「這欄要完整顯示」「這欄短，縮到剛好即可」「其餘平分」。換算交給框架依實際寬度處理。

**為什麼表格的欄寬以程式計算，不只使用 CSS**
「最小」欄要縮到內容寬，但上限是預設欄分到的那一份，而那一份要等其他欄排完才知道。瀏覽器的表格排版無法表達這種依賴其他欄的上限。因此程式量出各欄的內容寬後算好寬度，以固定欄寬的排版套上，並在資料或寬度改變時重算。

**為什麼表格放不下時，預設欄的下限為「最大欄也算作一份」，且兩種分法都計算**
- 只扣掉最大欄再均分時，最大欄接近畫面寬，便會把預設欄擠到幾乎沒有寬度
- 把最大欄也算作一份，預設欄便保有合理的寬度，代價是表格超出畫面、須橫向捲動
- 兩種分法在「一份等於最大欄的平均寬」時相等。取較大者即在該處平順地切換，預設欄的寬度不因最大欄差幾 px 而跳動
- 全部放得下時只用前者，表格不會因此超出畫面
- 曾考慮以固定寬度（例如若干字寬）作為切換的門檻。但切換後的寬度可能比切換前窄，仍須比較兩種分法

**為什麼表格的換行只取代截斷，且為整張表一個開關**
- 換行若改變欄寬的計算，例如令最大欄也均分寬度，三種設定中便沒有一種能保證完整顯示於一行
- 若改為「同一列有其他格撐高時才換行」，須逐列先排版一次、量出高度再決定，同一欄也會有的列換行、有的列截斷
- 只取代截斷時，欄寬照舊，只改變放不下時的顯示方式
- 須保持一行的短欄設為最大即可，因此不另設逐欄的開關

**為什麼表格的固定欄不改變欄寬，表頭也不固定於上方**
- 固定只決定捲動時哪幾欄留在原處。若同時改變欄寬，同一張表加上 `fixed` 後版面便會不同
- 固定欄的位置直接取已算好的欄寬，以 `position: sticky` 實作，不另外量測
- 表頭固定於上方，須讓表格自己有高度並在其中捲動：橫向捲動的外框會使整頁捲動時的 sticky 失效。這與詳細頁中隨整頁捲動的子表表格不合

**為什麼詳細頁欄位的排法是全站設定，再由頁面覆寫**
- 同一個 App 的詳細頁通常維持一致的版面，因此預設值放在 `config/app.ts`，與 App 名稱、登入方式等全站設定並列
- 有標頭與欄位動作的頁面，左右並排時左側顯得空，才由該頁改為上下兩行
- 與欄位順序相同，採「預設加上頁面覆寫」的模式
- dashboard 的窄面板放不下兩欄，因此不論設定一律上下兩行

**為什麼列表的動作按鈕不放在 `<a>` 中**
`<a>` 內含互動元素是無效的 HTML。

**為什麼有 `CountLabel` 這個元件，且不使用 `v-chip`**
- 分組標題與子表區塊的標題須外觀相同
- `v-chip` 的內距與行高隨外層的標題樣式變化，數字無法置中
- 標籤的底色以 `on-surface` 疊上透明度，疊在 `bg-surface-light` 的分組標題上也看得出來

**為什麼 gallery 沒有圖片時以灰色方塊佔位**
格線才會對齊。

**為什麼 `ViewActions` 在一般頁面不另外繪製文字按鈕的圖示**
上千列的列表才不會多出同樣數量的 `v-icon`。只有儀表板的窄面板需要這個圖示。

**為什麼 `DataCard` 的替代高度不寫死**
各層可以隱藏，卡片的高度差異大。

**為什麼 `ListPage` 不決定每一列的外觀**
每一列的呈現是這張表專屬的部分，由頁面決定。

**為什麼空列表不顯示「找不到資料」**
那是顯示單一列的頁面的狀態。空列表即顯示為空。

**為什麼不使用 `ListPage` 時須自行呼叫 `useListOrder`**
只有頁面知道畫面上的實際排列。

**為什麼表單中的虛擬欄位須先掛上 getter 再計算**
表單編輯的是那一列的一般複本。複製時，不可列舉的 getter（`$label`、父列、子列）都不會跟著複製，每次修改欄位也是建立新物件。直接以複本計算時，讀取父列的虛擬欄位會取不到資料。因此每次計算前，以 `store.withGetters` 重新掛上與快取相同的一套 getter。

**為什麼真實欄位沒有 `readonly`**
顯示上可與虛擬欄位共用同一條唯讀的路徑。但真實欄位另須從新增與修改的 payload 中排除，否則會覆蓋 Sheet 上的公式，`columnValues`、驗證與預設值也各須多一個判斷。目前沒有需求，待需要時再實作。

**為什麼 `ChildList` 的 slot 提供整批子列，不是一次一列**
`DataTable` 才放得進來。

**為什麼子表區塊的「展開」是一個頁面，不是就地展開**
換到四件現成的功能：
- 返回鍵回到詳細頁
- 有頁面的轉場動畫
- App Bar 的標題可以是子表的名稱
- `ListPage` 發布這份順序，因此從展開頁點進某一列時，上一列、下一列在同一個父列的子列之間切換

「展開」不寫列數，因為列數已顯示於標題旁的小標籤。「展開」也不依是否超過上限而出現或消失，位置固定，使用者無須猜測這次是否出現。子表區塊與展開頁皆沒有搜尋，子列多到須搜尋時，應至子表自己的列表頁。

**為什麼 `DetailPage` 不支援插在兩個欄位之間**
`DetailPage` 須把欄位切段顯示，`DataDetail` 須能只繪製部分的欄位，為了罕見的需求使兩個元件都變複雜。確實需要時，那一頁不使用 `DetailPage`，以現成的元件自行排列。

**為什麼 `FormPage` 的「找不到這筆資料」使用 `warning`**
網址打錯或資料被刪除都屬於正常的情況，不是錯誤。

**為什麼載入狀態的優先順序為 loading → error → empty**
與資料實際取得的順序一致。`FormPage` 的 loading → loadError → 找不到資料 → 表單也是如此。

**為什麼 `PageState` 的 `linear` 不卸載內容，動作失敗也不經過 `PageState`**
- 同步按鈕重新抓取所有已載入的表，`loading` 再次變為 true。此時若把列表換成進度條，`GroupedList` 的展開狀態會消失，畫面也會整個跳動
- `circular` 取代內容：顯示單一列的頁面重新抓取時，本來就沒有內容可保留
- 送出失敗、推送失敗等錯誤，須讓內容留在畫面上，表單不能消失

**為什麼 `GroupedList` 的外層不以 `v-if` 包住**
`loading` 一切換，便會整個卸載重建，展開狀態隨之消失。同步按鈕重新抓取所有已載入的表，這件事很常發生。

**為什麼 `GroupedList` 的分組內容左右外擴，且 `min-width` 改回 0**
- 展開與收合的動畫期間，Vuetify 於 `.v-list-group__items` 暫時設定 `overflow: hidden`。這無法移除，否則尚未展開的內容會溢出
- `v-list` 預設的 `overflow: auto` 也會裁切往右下的陰影
- 因此該層以負的 `margin-inline` 外擴，再以 `padding-inline` 抵銷，裁切的範圍便涵蓋陰影
- `min-width` 的預設值為 `min-content`。儀表板的窄面板中，展開的子分組會被不換行的標題撐得比面板寬

**為什麼調整陰影時須一併調整 `--list-card-shadow-extent`，且淡底以 `background-image` 疊上**
- 分組展開的動畫期間，裁切的範圍以此變數為準。不一併調整時，陰影會被裁切
- 淡底若使用 `background` 簡寫，元件的 scoped 樣式（帶有 `[data-v-…]`，較為具體）會將它覆蓋
- 淡底不寫成 `:root` 的變數：其值引用 `--v-theme-primary`，寫於 `:root` 時會先行求值，頁面中局部切換主題時不會跟著改變

**為什麼依 `select` 欄位分頁籤時，頁籤直接讀取該欄位的 `options`**
無須另外維護一份重複的清單。

**為什麼 `usePanelActive()` 與 `useCurrentTab()` 只接其中一個**
面板外的程式 `inject` 不到面板，面板中的程式也不知道自己是哪個頁籤，因此依程式所在的位置選擇。

**為什麼 `TabPage` 與 `DashboardPage` 不可互相嵌套**
- 兩者皆將搜尋登記於 App Bar，列表只加入最近的一層。兩層各自登記時，搜尋會互相覆蓋
- `TabPage` 將頁籤列登記於 App Bar，儀表板的多個面板無法共用

**為什麼 `TabPage` 關閉 `v-window` 的 `show-arrows` 與 `touch`**
- `show-arrows` 的預設值為 `undefined`，而判斷式為 `showArrows !== false`。不明確關閉時，內容上會疊一層左右箭頭
- `touch` 開啟時，可左右滑動切換頁籤，但會與 `DataTable` 的橫向捲動搶手勢
- `touch` 只綁定觸控事件，電腦上以滑鼠拖曳沒有反應。測試須使用 DevTools 的裝置模擬或實際的觸控裝置

**為什麼登入頁的 `meta` 須同時標示兩項**
沒有 `public: true` 時，登入頁本身會被導向登入頁。

**為什麼登入表單帶有 `autocomplete` 並包在 `<form>` 中**
瀏覽器的密碼管理員才會記住並自動填入。

**為什麼離開登入頁時清除密碼欄**
登入頁由 KeepAlive 保留，不清除時，密碼會一直留在記憶體中。

## 範本

**為什麼佔位字串為 `__table__`**
使用不像英文單字的標記，不使用 `template` 這類真實的單字：後者會連 Vue 的 `<template>` 標籤一起被取代，整個頁面便損毀。

**為什麼 `index.html` 的 `<title>` 須另寫一次 App 名稱**
靜態的 HTML 讀不到 TS 中的 `appName`。

## 儀表板

**為什麼手機寬 6 格、電腦寬 24 格**
估算以 1080×1920 的手機與 1920×1080 的電腦螢幕為準：
- 手機的 1080×1920 為實體像素，網頁中約為 360×640 的 CSS 像素，device pixel ratio 為 3
- 電腦於縮放 100% 時即為 CSS 像素，`v-container` 的最大寬度為 1400px

| | 寬的格數 | 每格約（含間距） | 內容區的高度約 | 面板的最小寬度 |
| --- | --- | --- | --- | --- |
| 手機 | 6 | 55px（內容區寬約 330px） | 9.6 格 | 2 格 |
| 電腦 | 24 | 57px（內容區寬約 1368px） | 15 格 | 2 格（約 106px，與手機相近） |

- 6 與 24 皆可二等分與三等分，24 另可四、六、八等分
- 兩者為 1:4，手機的半寬（3 格）於電腦上為 12 格
- 兩者每格的實際大小相近，「高幾格」於手機與電腦上的實際高度也相近

偏離基準的常見情況，結論不變：
- 較長的手機（例如 20:9，網頁中約 360×800）約 12 格高
- 開啟 125% 縮放的筆電（網頁中約 1536×864），`v-container` 的最大寬度降為 1000px，每格約 41px，約 16 格高

**為什麼手機或電腦的排版只由 `useCompactLayout()` 判斷**
JS 與 CSS 依同一個判斷，不會一邊是手機、一邊是電腦。判斷規則只寫在該 composable 中，日後改為依內容區寬度或依裝置判斷時，只須修改一處。

**為什麼暫時沿用 Vuetify 的 `mobile`，不使用 `platform`**
- `mobile` 依視窗寬度判斷，視窗大小改變時即時更新
- `platform` 只在啟動時比對一次 user agent，且 iPadOS 預設送出 Mac 的 user agent，不適合用於判斷平板
- 代價是平板直放（例如寬 820px）被視為手機，6 格時每格約 130px，過大。門檻留待日後調整

**為什麼手機的自動高度最多 8 格**
- 16:9 的手機內容區約 9.6 格高，8 格約佔螢幕的 69%
- 20:9 的手機約 12 格高，8 格約佔 56%
- 兩者皆低於一個畫面，面板上下總留有空間捲動整頁
- 內容很少的面板依內容撐開，不會撐到 8 格

**為什麼電腦的自動大小為寬 8 格、高 7 格，且高度固定**
- 一個畫面可顯示 3×2 個面板：兩排共 14 格，內容區約 15 格高
- 高度固定、不依內容撐開，同一排的面板才會對齊，第二排不致錯落
- 小外殼約佔一格，內容實際可用約 6 格：1920×1080 時約 340px，deck 約可顯示 4–5 列

**為什麼各面板的位置由 JS 計算**
CSS grid 遇到座標重疊時，直接讓面板疊在一起，既不警告也不挪開。因此位置由 `placePanels` 依排版規則算出，CSS 只依結果繪製。

**為什麼窄版的門檻為 3 格以下（寬度小於 200px）**
- deck 一行的 4 個圖示按鈕連同內距約 172px，card 約 160px
- 3 格（手機約 165–180px，電腦約 150–166px）放不下，4 格（約 200px 以上）可容納
- 手機與電腦每格的大小相近，以同一個門檻涵蓋兩者
- container query 只能使用長度，因此各元件各寫一次 `200px`

**為什麼部分內容於窄面板中不另外處理**
- table 本來就用於檢視完整的欄位，於面板內橫向捲動即可
- gallery 的格線已依寬度減少欄數
- 圖表依容器的寬度自行縮放
- profile 的標題與副標已以省略號截斷，⋮ 的選單 teleport 至 `body`，可超出面板
- deck 窄版時標題與副標上下排列，高度與原本的兩行相近，因此沿用同一個替代高度

**為什麼窄版的動作列先改為圖示，仍放不下才換行**
每個 `PageAction` 皆有 `icon`，改為圖示即可在不換行的前提下放進較多的動作。

**為什麼展開按鈕放在各面板的小外殼，不放在 App Bar**
未關注的面板也可直接展開。

**為什麼展開以同一個網址推入一筆 history，不換到該表自己的頁面**
- 儀表板的面板未必有對應的獨立頁面，且互動篩出的結果會遺失
- 網址相同時，KeepAlive 不重建此頁，面板中的狀態皆保留
- 換頁動畫以 View Transitions 截下前後的畫面，網址相同的展開也適用，無須另寫動畫

**為什麼展開與否依 history 的 state 決定，展開按鈕只推入 history**
以下情況因此無須另外處理：瀏覽器的下一頁再次展開、從展開的面板進入詳細頁再返回時仍為展開、重新整理後也維持展開。

**為什麼展開時 App Bar 的標題由儀表板指定**
頁面以元件 import 時，讀不到自己 `<route>` 的 `meta.title`。`_ref/` 中的列表也沒有路由。

**為什麼互動的選取每張表各記一列，不是全頁一列**
選取父列後，再於篩出的子列中選取一列，父列的選取不會被覆蓋。

**為什麼選取狀態不寫入網址**
儀表板與其他頁面同樣由 KeepAlive 快取。離開後再回來（例如從面板進入編輯頁再返回），選取仍保留，無須額外處理。

**為什麼父列的選取改變時，清除子表的選取**
原本選取的子列可能已不在新的篩選結果中。

**為什麼選取的那一列被搜尋隱藏時，仍保留選取**
子表照樣只顯示它的子列，不因輸入而跳回全部的子列。

**為什麼選取只連動一層**
避免連鎖過深。

**為什麼篩選條件往下連動多層，選取卻只連動一層**
篩選條件明確指定了哪一張表的哪一欄，子列只檢查「父列是否符合」，不會被要求自己也符合父表的欄位，因此逐層往下傳仍不會有歧義。選取改變時會清除子表的選取，連動多層會使一次點擊改變過多面板。

**為什麼篩選條件只往下連動**
往上會有歧義：父列有多列子列，只有其中一列符合時，父列是否符合沒有一致的答案。

**為什麼父表有條件時，ref 為空的子列不顯示**
沒有父列的子列無法證明自己符合父表的條件。

**為什麼搜尋字串不跨表連動**
搜尋是一串文字，每張表比對自己的欄位。跨表時須決定子列與父列之間為「且」或「或」：「且」常使子表變空，「或」使搜尋結果混入不含搜尋字串的列。維持每張表各自比對，結果與一般列表相同。

**為什麼子表的篩選抽屜提示上層的條件**
子表本身沒有條件，列卻變少，使用者不知道原因，也不知道從哪裡清除。

**為什麼子表的篩選選項不依上層的條件縮減**
與「其他欄位的條件不縮減選項」相同：選項隨其他條件消失時，使用者難以回頭修改。

**為什麼多選時以捕獲階段鎖定其他面板，不使用 `inert`**
`inert` 使整個面板不參與 hit testing，面板自己的捲動可能一併失效，滾輪改為捲動整頁。改以捕獲階段攔下點擊與長按，面板的捲動不受影響。

**為什麼面板只在轉場進行中才命名**
平時帶有 `view-transition-name` 時，換頁時面板會成為獨立的轉場對象，不隨整個畫面一起滑動。

## 決定不做

評估過而決定不採用的做法，記錄於此以免重複討論。有回頭重新評估的時機時，附於條目末尾。只是延後、時候到了就做的項目，仍留在 ROADMAP 的「未完成」。

**路由驅動的通用頁**
即 `src/pages/[table]/` 下的四個通用頁讀取 `schemas[route.params.table]`，新增一張表只須撰寫 schema 並註冊一行。

- 當初的動機是四個頁面檔幾乎相同。但版型元件已將這些樣板抽出，頁面檔剩下的每一行都在說明「這是哪張表、有哪些動作」
- 再進一步只換得「連四個小檔都不必複製」，而這本來就是 `template/` 的職責
- 代價：
  - 頁面層失去 Row 型別，版型元件的泛型 slot 便失去作用
  - eject 的粒度變為整張表的資料夾，因為靜態的路由段會蓋過動態段
  - schema 開始帶有 UI 設定（`listFields`、`detailTables`）

**回頭重看**：表增加到十幾張，而且大多相同時。

**佇列持久化**
佇列只存在於記憶體中。重新整理、當機、分頁被系統關閉時，未推送的變更會遺失，`beforeunload` 只擋得住主動關閉分頁。單人使用、推送只是一個按鈕，可以接受。

須實作時的做法：
- 存入 `localStorage`。`values` 進入佇列時已序列化，可直接 `JSON.stringify`
- 流程期間暫停寫入：磁碟上停在流程開始前的狀態，被關閉後再開啟即等於自動回滾
- 唯一成本較高的是啟動後須將佇列重新套用至從後端抓回的 `rows`，須有一個只處理部分欄位的 `coerceRow`

**回頭重看**：確實遺失過一次未推送的變更時。

**離線寫入佇列**
即離線時照常操作，連線後再送出。須要 IndexedDB、寫入佇列與衝突處理一整套，成本結構與佇列持久化相同，而且多了「離線期間看到的資料可能已經過期」的問題。**回頭重看**：確實經常在沒有網路的地方使用時。

**推送失敗的逐列補償**
即記錄哪幾列已成功，只重送失敗的部分。推送為全有全無，不會有「成功了幾列」的情況。id 由前端發號、`create` 定義為冪等，整批重送本來就安全。

**衝突時將佇列重新套用至新資料**
即衝突時保留未推送的修改，套用至重新抓回的資料上。成本與佇列持久化相同。衝突時的兩條出路（放棄並重抓、強制推送）已足夠。

**連續動作中返回即回到上一步，而非整條取消**
代價為三件事，加起來等於一個多頁精靈：
- 每一步改為 `push`，且結束後須清除歷史
- 存檔點須由一格變為一疊，每一步可單獨收回
- 上一步的表單須帶著使用者上次填寫的值重新開啟

**回頭重看**：確實有三步以上、經常須回頭修改的流程時。

**編輯表單的預設值通道**
`useEditForm` 不讀取 `navigationDefaults()`。因此編輯表單可以作為流程的一步，但無法把上一步的結果預先填入。目前想不到需要的情境。

**連續動作的進度指示**
即「第 1 步／共 2 步」。流程最多兩三步，每一步皆為完整的一頁，App Bar 上有自己的標題。

## 已知的權宜作法

目前採用、但已知並不理想的做法。這些不是待辦事項。

**`refTable` 沒有型別檢查**
`refTable` 只存放代稱字串，不保證確實存在於 `schemas`。為了避免 `schema/types.ts` 反過來 import `schema/index.ts` 造成循環依賴，目前接受這個缺口。

**`template/` 不在 `src/` 中**
因此 lint 與型別檢查不掃描範本，元件的 props 改變時，範本不會自動報錯。目前以「把範本複製為一張暫時的表，建置通過後再刪除」的方式手動驗證。

**刪除時短暫閃現「找不到這筆資料」**
快取更新之後、返回動畫進行期間，詳細頁的 row 已為 null。那一列確實已不存在，語意上可以接受，因此不為此增加凍結顯示的機制。
